# 룬PT 모듈화 이관 프롬프트 (트레이너 저장소용)

이 프롬프트는 `upvible/Rune-PT`를 작업하는 Claude Code에 그대로 붙여 넣는다.

- 운영 앱: `upvible/Rune-PT` (`index.html` 약 545KB 한 파일, `avatar/`, `sw.js`, GitHub Pages `https://upvible.github.io/Rune-PT/`). 지금까지 GitHub 웹 업로드로 관리했다.
- Path A: `chjisceo/rune-pt`의 `feat/path-a-design` 브랜치. 운영 `index.html`을 바탕으로 Harry가 만든 모노레포(`packages/core` + `apps/web`, Vite·React·TypeScript)다. 화면, 3D 근육 뷰어, 온보딩은 완성돼 있다. 로그인, Supabase 저장·동기화, 실제 티어 규칙, 트레이너 화면 대부분은 아직 데모 데이터다.

목표는 운영 앱의 모든 기능을 Path A 구조로 옮기는 것이다. 옮기는 동안 운영 앱은 지금 주소에서 계속 돌아가야 한다. Path A는 같은 사이트의 `/next/`에서 따로 확인하고, 기능이 다 맞은 뒤에만 첫 화면을 바꾼다.

## 지켜야 할 것

- 단계마다 브랜치를 따고 PR을 연다. `main`에 바로 올리지 않는다. GitHub 웹 업로드로 파일을 덮어쓰지 않는다.
- 단계를 건너뛰지 않는다. 앞 단계의 PR이 머지되고 실제 사이트에서 확인된 뒤 다음 단계를 시작한다.
- 운영 앱의 동작을 바꾸는 단계는 1단계뿐이고, 그것도 파일 위치만 바꾼다.
- `chjisceo/rune-pt`와 `upvible/Rune-PT`는 커밋 조상이 다르다. `git merge`, `git pull`로 합치지 않는다. 파일을 복사한다.
- Path A의 `AGENTS.md`, `PRODUCT.md`, `DESIGN.md` 규칙을 따른다. 특히 `service_role`·`sb_secret` 키 금지, 외부 문자열 `escapeHtml()`, `postMessage`는 `location.origin`만, 3D 뷰어에 신체·개인정보 전송 금지, 나이 8~90세와 키·체중·체지방 범위 유지.
- `SB_URL`, `SB_KEY`, `APP_URL` 값을 PR 본문, 커밋 메시지, 로그에 적지 않는다.
- 사용자(트레이너)가 GitHub·Supabase 설정 화면에서 해야 하는 일은 대신 추측하지 말고, 무엇을 어디서 누르는지 알려 주고 기다린다.

## 준비

1. 운영 저장소를 git으로 받는다. 로그인이 안 돼 있으면 사용자에게 `gh auth login`을 안내한다.
2. Path A는 운영 저장소 밖에 받는다.
   ```sh
   git clone --branch feat/path-a-design https://github.com/chjisceo/rune-pt.git ../rune-pt-ref
   ```
3. 3D 근육 모형 `stayfit-muscle-skeleton.glb`(약 4.97MB)는 `.gitignore`로 빠져 있어 저장소에 없다. Harry에게 따로 받는다. 받기 전에는 2D 근육 지도와 포스터로 동작해야 한다.
4. 지금 사이트에서 아래 "기능 대조표"의 항목을 회원·트레이너 계정으로 한 번씩 눌러 보고 결과를 `docs/parity.md`에 적는다. 이 파일이 끝까지 기준이 된다.

## 1단계: 운영 `index.html`을 여러 파일로 나누기

스크립트가 약 519KB라 AI가 한 번에 읽지 못한다. 원래 따로 있던 파일을 이어 붙인 것이라 구분 주석이 남아 있다. 빌드 도구 없이 원래 파일로 되돌린다.

| 새 파일 | 옮길 부분 (`index.html`) |
|---|---|
| `css/app.css` | 첫 번째 `<style>` 안쪽 전부 |
| `js/rune-tier-core.js` | `/* ===== 티어 코어 (rune-tier-core.js) ===== */`부터 다음 구분 주석 바로 앞까지 |
| `js/rune-routine.js` | `/* ===== 루틴 엔진 (rune-routine.js) ===== */`부터 다음 구분 주석 바로 앞까지 |
| `js/catalog.js` | `/* ===== 종목 카탈로그 (catalog.js) ===== */`부터 다음 구분 주석 바로 앞까지 |
| `js/app.js` | `/* ===== 앱 ===== */`부터 첫 `</script>` 바로 앞까지 |

- 글자를 바꾸지 않고 잘라서 옮기기만 한다. 포매터를 돌리지 않는다. 새 JS 파일을 순서대로 이어 붙이면 원래 스크립트와 같은지 명령으로 확인하고 결과를 PR에 적는다.
- 일반 `<script src>`로 표의 순서대로 `</body>` 앞에 둔다. `type="module"`을 쓰지 않는다. `app.js`는 최상위 이름을 전역으로 공유하므로 이 단계에서 더 쪼개지 않는다.
- `<head>`의 테마 선적용 스크립트, supabase-js CDN 태그, 서비스워커 등록은 제자리에 둔다.
- `sw.js`의 `SHELL`에 있는 `manifest.webmanifest`, `icon-192.png`, `icon-512.png`는 저장소와 사이트에 없다(404). `cache.addAll`은 하나라도 없으면 실패하므로 지금 서비스워커 설치가 깨져 있다. `SHELL`을 실제로 있는 파일(`./`, `index.html`, `css/app.css`, `js/*.js`)로 바꾸고 `V`를 `rpt-v3`로 올린다. 아이콘과 매니페스트를 새로 만들지는 사용자에게 묻는다.

끝난 기준: `docs/parity.md`의 항목이 시작 전과 같다. 기존 `rpt1`이 있는 브라우저에서 기록이 그대로다. 콘솔에 새 오류가 없다.

## 2단계: Path A를 저장소에 들이고 `/next/`로 배포

`../rune-pt-ref`에서 복사한다: `apps/`, `packages/`, `package.json`, `package-lock.json`, `tsconfig.base.json`, `AGENTS.md`, `PRODUCT.md`, `DESIGN.md`, `CLAUDE.md`, `design-review/proposed/`. `.gitignore`는 합친다. `node_modules/`, `dist/`, `.impeccable/`은 복사하지 않는다. 운영 파일(`index.html`, `css/`, `js/`, `avatar/`, `sw.js`)은 그대로 저장소 루트에 둔다.

같은 도메인에서 돌기 때문에 아래를 먼저 고친다.

- 저장 키: `apps/web/src/services/localRuneRepository.ts`는 `rpt1`을 운영과 다른 모양(`{version, snapshot}`)으로 쓴다. 그대로 두면 `/next/`를 여는 순간 회원의 운영 기록을 덮어쓴다. 키를 `rpt-next`로 바꾸고, 4단계에서 모양이 같아지기 전에는 `rpt1`을 읽지도 쓰지도 않는다. `rune-theme`은 공유해도 된다.
- 경로: `vite.config.ts`에 `base: '/Rune-PT/next/'`를 둔다. 코드의 절대 경로 `/models/...`, `/draco/`는 `import.meta.env.BASE_URL` 기준으로 바꾼다.
- 배포: GitHub Actions 워크플로 하나로 사이트를 조립한다. 루트에는 운영 파일을 그대로 복사하고, `npm ci && npm run typecheck && npm run build` 결과(`apps/web/dist`)를 `next/`에 넣어 Pages에 올린다. 사용자에게 Settings → Pages → Source를 "GitHub Actions"로 바꾸도록 안내한다. 바꾼 뒤 운영 주소의 파일이 바뀌지 않았는지(같은 내용이 내려오는지) 확인한다.
- GLB는 저장소에 넣지 않는다. 워크플로에서 쓸 수 있게 어디에 둘지(GitHub Release 첨부 등) 사용자와 정한다. 정하기 전에는 `/next/`에서 3D 버튼이 "모형을 열지 못했어요"로 끝나도 된다.

끝난 기준: 운영 주소가 1단계 그대로 동작한다. `/next/`에서 Path A 데모가 열린다. `/next/`를 연 뒤에도 운영 기록이 그대로다.

## 3단계: 도메인 로직을 `packages/core`로 옮기기

Path A의 `tierCore.ts`는 Epley 1RM과 볼륨 정도만 있다. 진짜 규칙은 운영의 세 모듈에 있다.

- `js/rune-tier-core.js` → `packages/core/src/tier/` (나이·성별 계수, 풀업, 달리기, 승급, 별·티어)
- `js/rune-routine.js` → `packages/core/src/routine/`
- `js/catalog.js` → `packages/core/src/catalog/` (`EXERCISES` 18종, 카탈로그 읽기·쓰기)
- `js/app.js` 안의 순수 계산(DOM·네트워크 없는 함수: `recommend`, `plan`, `vol`, `fmt`, 1RM 계산 `rm*`, 등급 `grade*`, 통계 집계 `st*` 등)도 같은 원칙으로 옮긴다.

규칙:

- 동작을 바꾸지 않고 타입만 붙인다. 개선은 별도 PR이다.
- 세 모듈은 UMD라 Node에서 `require`로 그대로 불린다. 테스트(vitest)를 추가해 같은 입력에 원본 JS와 새 TS의 결과가 같은지 비교한다. 경계값(나이 8·17·18·90, 무게 0, 반복 1)을 넣는다.
- Path A의 기존 `tierCore.ts` 함수가 겹치면 원본 규칙 쪽으로 맞춘다.
- 운영 루트는 이 단계에서도 `js/` 원본을 그대로 쓴다.

## 4단계: 저장소 어댑터 (Supabase)

`packages/core/src/repository.ts`의 인터페이스를 운영 데이터 모양에 맞게 다시 정한다. 기준은 Path A의 스냅샷이 아니라 운영의 `rpt1`과 서버 테이블이다.

- `rpt1` 최상위: `user`, `level`, `sessions`, `more`, `curNo`, `drafts`, `profile`, `tiers`, `equip`, `runs`, `adm`, `wm`, `mode`. 오늘 초안 `drafts[날짜].slots[].sets[]`의 `w`, `r`, `t`, `done`, `v`, `lr`, `w2`, `r2`, `car`와 세트 타입 `W` `M` `F`(옛 값 `N`→`M`).
- 테이블: `app_state`, `body_measurements`, `exercise_catalog`, `exercise_standards`, `exercise_standards_active`, `member_body`, `profiles`, `push_subscriptions`, `routine_gifts`, `workout_sessions`. RPC: `member_link_*`, `trainer_link_*`, `trainer_member_*`, `trainer_multi_workout_alerts`, `trainer_record_*`, `my_record_views`, `push_mark_end`. 쿼리는 운영 `js/app.js`의 것을 그대로 옮긴다. 스키마를 바꾸지 않는다.
- 동기화(`syPull`, `syMerge`, `syFlush`, `queueSync`)는 3단계와 같은 방식으로 core에 옮기고 원본과 결과를 비교한다.
- 키는 publishable 키 하나를 빌드 환경변수(`VITE_SUPABASE_URL`, `VITE_SUPABASE_KEY`, Actions 변수)로 받는다.
- 로그인: `/next/`용 고정 `APP_URL`을 따로 둔다. 사용자에게 Supabase Auth의 Redirect URL 허용 목록에 `/next/` 주소를 추가하도록 안내한다. 운영 `APP_URL`은 바꾸지 않는다. 복귀 후 `code`, `access_token`은 `history.replaceState`로 지운다.
- 체험(데모) 로그인 버튼과 `sampleData`는 이 단계에서 실제 데이터로 대체하고, 데모는 개발 모드에서만 보이게 한다.
- 저장 키 `rpt-next`를 `rpt1`로 바꾸는 것은 모양이 같다는 테스트가 통과한 뒤 한 PR로만 한다.

## 5단계: 화면을 하나씩 옮기기

한 PR에 한 묶음이다. 각 PR은 같은 계정으로 운영 주소와 `/next/`를 나란히 눌러 `docs/parity.md` 해당 줄을 채운다. 순서:

1. 회원 오늘 운동: 세트 기록·저장, 오늘 두 번째 운동(`newsess`), 운동 방식(`wm`), 휴식 타이머
2. 달력, 통계(기간 추이·부위별 세트·분포·주요 운동·월간 리포트·측정)
3. 선물함 받기·수락, 내 정보, 온보딩, 테마
4. 1RM 계산, 등급·승급 시험, 달리기 기록, 체성분 측정, 장비·아바타(`avatar/`는 `postMessage` 규칙대로, 성별 등 프로필 미전송)
5. 트레이너: 회원 목록·편집·합치기, 달력, 하루 수업, 퀘스트·인장, 기록 피드, 카탈로그 편집, 회원 연결 요청, 선물 보내기, 잔여 수업 대조, 운동 알림
6. 구글 캘린더 불러오기, 푸시 알림, 서버 선택, 서비스워커

옮길 때 원본 화면 함수(`viewToday`, `viewCal`, `viewStat`, `viewMe`, `viewAdm`, `viewMem`, `viewACal`, `viewDay2`, `viewQuest2`, `viewRec`, `viewCat`, `viewServers` 등)를 읽고 같은 데이터·같은 결과를 내도록 만든다. 생김은 Path A와 `design-review/proposed/`를 따른다.

## 6단계: 첫 화면 바꾸기

`docs/parity.md`가 모두 통과하면 사용자에게 확인을 받고, 루트가 Path A를 내보내도록 워크플로를 바꾼다. 옛 앱은 `/legacy/`에 일정 기간 남긴다. 서비스워커 캐시 버전을 올린다. 이 결정은 사용자가 한다.

## 기능 대조표 (`docs/parity.md` 시작점)

| 영역 | 항목 |
|---|---|
| 로그인 | 카카오, 구글, 카톡 인앱 안내, 로그아웃, 첫 로그인 온보딩 |
| 회원 운동 | 종목 고르기, 세트 추가·삭제, 무게·횟수, 완료 체크, 오늘 저장, 두 번째 운동, 운동 방식, 추천 |
